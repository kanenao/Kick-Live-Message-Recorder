# α版・製品版のリリース運用方針

このプロジェクトは、将来的にα版と製品版（安定版）を分離して配布する。

## 目的

- α版：新機能を早く取り込み、開発者・希望するテスターが先行検証するチャンネル
- 製品版：α版で検証を終え、重大な既知不具合がなく、安定性基準を満たした変更だけを配布するチャンネル

「不具合ゼロ」は保証できない。製品版は、既知の重大不具合がなく、定義したテストに合格し、残る既知の制限をリリースノートに明記した版とする。

## バージョンと配布チャンネル

| チャンネル | バージョン例 | 用途 |
| --- | --- | --- |
| α版 | `0.2.2-alpha.57` | 新機能・修正の先行テスト |
| 製品版 | `1.0.0`、`1.0.1` | 安定性確認済みの一般配布 |

### バージョン番号の決め方

バージョンは `MAJOR.MINOR.PATCH-alpha.N` 形式とし、`MAJOR.MINOR.PATCH` とα版の連番 `N` を別々に管理する。現在の `0.2.2-alpha.57` は、LIVE音声FFmpegの無進捗監視と自動復旧を追加したPATCH更新である。次回以降も変更内容・開発の成熟度・互換性への影響を見て判断する。

- **PATCH**：既存機能の不具合修正、安定性・性能改善、小規模な調整（今回：`0.2.2-alpha.57`、次回例：`0.2.3-alpha.58`）。
- **MINOR**：互換性を保った主要機能の追加・拡張、開発上の大きな節目（次回例：`0.3.0-alpha.58`）。
- **MAJOR**：安定版公開後の大きな互換性変更。初回の `1.0.0` は、製品版の安定性基準を満たした段階で判断する。

α版の `N` は、PATCH／MINOR／MAJORが変わってもリセットしない。開発の各回で `alpha.52 → alpha.53 → alpha.54 → alpha.55 → alpha.56 → alpha.57` と継続して増やす。したがって、次回は小規模修正なら `0.2.3-alpha.58`、主要機能追加なら `0.3.0-alpha.58` とする。現在の番号を機械的に固定せず、開発内容を確認して更新する。

- α版のGitHub ReleasesはPre-releaseとして公開する。
- 製品版のGitHub Releasesは通常のLatest Releaseとして公開する。
- α版と製品版の更新確認先・更新チャンネルを分離し、製品版にα版が自動配信されないようにする。
- 製品版の更新は製品版チャンネル内の修正版だけを対象とする。
- バージョン番号は、タグ、`package.json`、アプリ画面、インストーラー名、リリースノートを必ず一致させる。

## 開発と昇格の流れ

1. 機能開発は作業用ブランチで行い、α版開発ラインへ取り込む。
2. α版としてビルドし、GitHub Actionsの型チェック・ビルド・Windowsインストーラー作成を確認する。
3. 実際のWindows環境で主要機能と既存機能の回帰テストを行う。
4. リリース候補を固定し、重大な不具合が見つかった場合はα版で修正して再検証する。
5. 合格した特定コミットだけを製品版ラインへ昇格する。α版の未検証機能を一括で製品版へ流し込まない。
6. 製品版のタグと通常Releaseを作成し、製品版ユーザーへ配布する。

## 製品版への昇格条件

### 必須チェック

- [ ] TypeScript型チェックと本番ビルドが成功
- [ ] Windows x64インストーラーの作成と新規インストール確認
- [ ] 既存バージョンからのアップデート確認
- [ ] アンインストール・再インストール後の設定／録画データの扱いを確認
- [ ] 配信検知・録画開始／停止・自動再接続の確認
- [ ] コメント受信・保存・時刻同期の確認
- [ ] コメント付き動画の生成とプレビューの確認
- [ ] 配信記事の生成・更新・保存・削除の確認
- [ ] Ollama未導入・モデル未導入・AI接続失敗時のエラー表示確認
- [ ] ネットワーク切断、API制限、配信終了、録画ファイル異常などの異常系確認
- [ ] 長時間録画および複数チャンネル運用の負荷確認
- [ ] 既知の重大不具合が残っていないことを確認
- [ ] リリースノートに既知の制限・注意事項を記載

CI成功だけでは製品版への昇格条件を満たしたことにしない。実機での確認結果も記録する。

## 不具合修正の取り込み

- 製品版で発生した不具合は、影響範囲を絞った修正を製品版側で検証する。
- その修正をα版にも戻し、同じ不具合が再発しないようにする。
- α版だけにある未検証の新機能を、製品版へ自動的に取り込まない。
- データ形式や設定形式を変更する場合は、バックアップ・移行・旧版互換性を確認する。

## 自動更新とデータ保護

- α版と製品版の更新メタデータ／配信先を混在させない。
- 製品版ユーザーが明示的にα版へ切り替えない限り、α版へ更新されないことをテストする。
- α版から製品版へ移る場合は、設定・保存済み記事・録画・コメントログを保護し、移行前バックアップと互換性を確認する。
- 更新失敗時にユーザーデータを消さない。アプリ本体の再インストールで録画データを削除しない設計とする。

## 現在の運用方針（α版のみ）

- 今後はα版だけを開発・テスト・ビルドし、公開は `v*-alpha*` タグを作成したときに限る。過去に公開済みのβ50は変更しない。
- 過去に公開済みの最終β版：`v0.1.0-beta.50`（履歴として保持）
- 現在のα57開発基準：`0.2.2-alpha.57`。作業ブランチは `feature/alpha52-broadcast-newspaper-layout`（α52で着手した新聞レイアウト改善を継続中）
- 製品版の完成・公開時期は未定。製品版用ブランチ、製品版向けRelease、自動更新チャンネルはまだ作成・有効化しない。
- α版のGitHub Releasesは引き続きPre-releaseとして扱い、バージョンは `MAJOR.MINOR.PATCH-alpha.N` 形式とする。3つの数字は開発内容に応じて更新し、`alpha.N` は独立した連番として継続する。
- GitHub Actionsのリリーステスト対象タグは `v*-alpha*` のみとし、通常の製品版タグ（例：`v1.0.0`）ではα版のリリーステスト／公開ジョブを起動しない。
- CIでは `scripts/test-release-tag-policy.mjs` を実行し、α版タグ・α版リリースブランチ・公開ジョブの振り分け例を自動テストする。
- `release/*-alpha*` ブランチへのpushは検証ビルドのみとし、GitHub Releaseを公開しない。実際のα版Release公開は `v*-alpha*` タグpushだけで行い、ブランチpushからタグを自動作成しない（二重公開の防止）。
- 今後製品版へ移行する場合は、ユーザーの方針を改めて確認し、α版の検証結果を見てから別途設計・実装する。
- 既存の `main`、`release/*`、GitHub Actionsの公開条件は履歴を確認してから整理する。既存ブランチを確認なしに強制移動・削除・マージしない。
